## Beginner explanation and terms

Imagine keeping a recipe card beside a cake. The card names the ingredients, the steps and the intended test.
A manifest is that card for an experiment. A filename is only a label: its contents can change while the name
stays the same. A checksum adds a fingerprint of the actual bytes so a later reader can check for a change.

**Manifest:** a structured record describing an experiment. **Schema:** the rules for that record's fields.
**Provenance:** information about how an output was produced. **Checksum or digest:** a compact value computed
from bytes. **SHA-256:** the hash algorithm used here. **Serialization:** turning a structured value into bytes.
**Evaluation protocol:** the declared procedure for testing a question. **Synthetic:** invented rather than observed data.

A schema version describes how to interpret a record. An experiment version distinguishes a revised experiment.
Changing the research question need not change the schema, but it should produce an identifiable new record.

## Mathematics and independent example

Let B_i be the bytes of source file i and d_i the digest stored in the manifest. Compute h_i = SHA256(B_i).
The integrity gate accepts only if metadata is valid and h_i = d_i for every declared file i. Missing files fail.
This is an exact comparison of digest strings, without a floating-point tolerance.

SHA-256 returns 256 bits. Each hexadecimal character represents four bits, so the stored digest has
256 / 4 = 64 hexadecimal characters. Distinct inputs can theoretically share a digest: the output space is
finite, whereas possible input files are unbounded. A digest is not a mathematical proof of uniqueness.

Our independent known-answer test uses the exact three bytes abc, without a newline. Its expected digest is
ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad.
The expected value is a literal test constant, not calculated by the function being checked.

## Implementation and input validation

The reusable module is src/quant_research/validation/manifests.py. It has separate operations to load JSON,
validate metadata, serialize a record and verify its source files. Validating a record alone does not read
source files or establish that their bytes match. The experiment explicitly invokes source verification.

Version 1 requires schema_version, experiment_id, data_kind, question, hypothesis, information_period,
evaluation_protocol and sources. Only integer 1 is supported as the schema version; true and 1.0 are rejected.
Unknown fields fail rather than being silently ignored. Text must be nonblank. Data kind must be synthetic or
real, so mixed data needs separate explicit records for now. Period and protocol text remain human assertions.

Each source requires a unique normalized relative POSIX path and a lowercase 64-character hexadecimal hash.
Absolute paths, parent traversal and ambiguous paths fail. Verification resolves paths beneath the supplied
root and rejects missing files, directories and symlinks escaping that root. Files must remain unchanged during
verification; this mechanism is not a security boundary against a concurrently hostile filesystem.

Python's JSON loader ordinarily accepts repeated object names with the last value winning. We instead reject
repeated names, including inside source records, so an ambiguous document cannot silently redefine a hash.
Serialization sorts object keys, uses two-space indentation and adds one final newline. Source-list order is
preserved. These are project conventions, not a universal canonical JSON format.

## Worked interpretation: a harmless-looking edit

Suppose the archived JSON ends with a newline. Appending one space does not change its parsed financial
meaning, but it does change its bytes. The pinned digest no longer matches and the verifier raises an error.
This is intentional: the contract is exact file identity, not semantic equivalence of JSON documents.

A failure is a prompt to investigate. It could mean an intentional formatting change, a revised experiment,
a stale file or an unintended edit. Do not regenerate the expected hash automatically just to pass the test.
For an intentional revision, retain the earlier version in Git history and record a new experiment ID with
new evidence. Verify historical manifests against the corresponding historical checkout.

## Limitations and interpretation

A checksum proves neither truth nor authorship. If a party changes both a file and its expected digest,
this comparison alone cannot reveal the replacement. There is no signature, trusted timestamp or access-control
system here. Declaring data real or synthetic is still an author assertion; the validator does not inspect markets.

The four-file manifest is a bounded provenance record, not a complete dependency graph or a fully captured
execution environment. A lock file does not record the entire operating system, hardware or compiler. Matching
sources does not establish licensing, point-in-time validity, absence of bias or successful reproduction.
Reproduction additionally requires executing the procedure and comparing outputs.

No empirical alpha is claimed. Q005a's fold bug remains open; use UTC-normalized inputs for Q001.

## What to explain in an interview

Start with the failure mode: a stored result and its filename can survive even after the input file changes.
Describe the schema validation gate separately from the source-integrity gate, then show the one-byte negative
test. Explain why the expected digest is trusted only as far as the stored record is trusted. Finish by stating
that correct provenance supports reproducibility but does not establish predictive value or a sound experiment.

## Check your understanding

1. Why is a filename insufficient to identify the source used in a result?

2. Why does SHA-256 produce 64 hexadecimal characters, and does that prove two files are identical?

3. Why are metadata validation and source verification separate operations?

4. Should an appended space fail the file checksum even if JSON still parses identically?

5. If every checksum matches, what remains unproven about the research?

## Suggested answers

1. The contents can change without renaming the file. A pinned digest records a fingerprint of the bytes
that the author intended to identify, allowing later changes to be detected against that reference.

2. There are 256 bits and four bits per hexadecimal digit, giving 64 digits. Matching hashes are strong
practical evidence of matching bytes under this use, but finite hash spaces permit theoretical collisions.

3. One validates the record's shape and declared values; the other reads the actual files. A well-formed
record can still point to missing or changed files, so the audit must perform both operations.

4. Yes. This contract identifies bytes, including whitespace and line endings. Semantic JSON comparison
would be a different contract and would require an explicitly defined normalization procedure.

5. Authorship, licensing, complete environment capture, data truth, leakage freedom, successful execution
and empirical validity remain unproven. The record helps investigate those questions; it does not answer them.
