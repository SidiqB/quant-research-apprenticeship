# Valid years can still overflow savings

12 October 2026 | C003a consolidation and readiness | Synthetic fixtures only

Sidiq review status: Not yet reviewed. Studied October 12; integrated October 13.

## Research question and hypothesis

Does accepting whole-year text guarantee a usable savings result? Hypothesis: no. Blank, fraction,
suffix and oversized text stop before calculation, while the largest accepted integer can reach
calculation and overflow. Valid zero is different from both kinds of failure.

This consolidates the existing functions after reproduction; the ledger starts with a later hand example.

## Beginner explanation and terms

A contract states which inputs and results a function permits. Parsing checks the original spelling
and whether its number fits an int. Calculation checks principal, rate, years and the finite result.
An exception reports that a normal result could not be supplied. A catch handles a particular error;
a return exits this trace before later statements execute. It must not manufacture a zero-year value.

Think of two separate questions. First, did the user supply an allowed whole count? Second, can this
model compute a permitted finite balance using that count? Passing the first does not answer the second.
The local variable starts at zero only to initialise storage. The error branches exit before using it.

## Assumptions, mathematics and hand example

P is principal in arbitrary money units; r is the fixed effective annual rate as a fraction; n is a
nonnegative whole count of model years. B(n) = P * (1+r)^n. Here P=1000 and normally r=0.05.
B(0)=1000; B(1)=1000+50=1050; B(2)=1050+52.50=1102.50. Python Decimal independently checks B(2).

At the tested int maximum, n=2147483647 is valid text and a valid integer. With r=0.05, the finite
double calculation fails. We need no enormous decimal balance to predict that failure: 1.05^20 > 2,
so after 20480 years the growth factor exceeds 2^1024, beyond the tested binary64 finite range.
The chosen horizon is far larger. This is a magnitude bound, not a measured financial loss.

With the same maximum n but r=0, B(n)=1000. The existing zero-rate branch returns principal directly.
This positive control shows why rejecting every large year count in the parser would change its contract.
The observed overflow describes this implementation and target, not every numeric representation.

| Fixed case | Parser result | Calculation result |

## Trace the C++ branches slowly

The fixed readiness_trace.cpp calls existing functions. Its helper accepts a label, original text and
rate. A const string reference lets it inspect text without changing it. int years = 0 initialises a
local variable; years = parse_whole_years(text) assigns it only if parsing returns normally.

The first try contains only parsing. invalid_argument means forbidden spelling, and out_of_range
means digit-only text beyond the representation. Each matching catch prints the reason and returns.
Thus neither error reaches compound_balance. Blank is not reinterpreted as zero.

After successful parsing, the helper prints the accepted integer. Its second try calls
compound_balance(1000.0, rate, years). A finite result is printed to two decimals. overflow_error
prints no balance. Unexpected exceptions are not hidden behind a generic successful outcome.

The main function makes eight explicit calls. It uses the already introduced numeric_limits to obtain
the target maximum. No input loop, vector, new class or CLI is added. Production sources stay unchanged.

Appending a decimal zero multiplies the represented positive maximum by ten in text; no C++ integer
overflow is used to form the out-of-range input. A fraction still has no defined accrual convention here.

## Costs, failure cases and limitations

The savings model assumes a fixed nonnegative rate, annual reinvestment and no intervening cash flows.
Fees, taxes and inflation are omitted; zero observed costs are not inferred. No traded instrument,
historical period, market sample, spread estimate, tuning or profitability result is present.

A fallback zero hides malformed input. A broad catch could confuse parsing and calculation errors.
Formatting two decimals is not exact-money arithmetic. This implementation can also reject an overflowing
intermediate factor even when another numerical method could produce a finite final value.

No length limit, external CLI hardening, cross-platform guarantee, all-input proof or coverage percentage
is established. Python and C++ share the written contract and fixture expectations. The current checks
support repository readiness for the next bounded lesson; they do not establish personal understanding.

## Interview explanation

I preserve original text until parsing checks spelling and range. A rejected input never reaches the
calculation. A valid integer can still overflow the financial model, so that model validates its own
result. Separate error paths explain which contract failed without silently substituting zero.

## Suggested answers

1. The parser throws on blank input. Its catch returns before the local value can enter the model.
The explicit string 0 instead passes parsing and gives a permitted horizon.

2. Integer representation and finite exponential growth are different constraints. The text fits int,
but the growth factor exceeds the tested double range; the model rejects it rather than returning infinity.

3. Zero rate means no growth, so the existing shortcut returns the validated principal. This is a
permitted calculation, whereas rejection supplies no result at all.

4. No. Repository evidence supports the next bounded lesson. Personal review is unconfirmed, and
principal/rate parsing, resource policy and the complete CLI remain future work.
