# Validate the clock before using the data

## Research question and hypothesis

Can a strict ingestion boundary reject malformed observations and invalid local timestamps without
silently choosing a clock interpretation? The hypothesis is that explicit offsets, verified against one
declared source zone, distinguish repeated times and reject missing times before UTC selection.

Yesterday's Q005a made selection chronological once inputs identify valid instants. It did not establish
whether a source's local clock label exists. Q005 completes this next boundary while lawful market-data
access remains unverified. Today's work is independent engineering research, not an empirical alpha test.

## Beginner explanation and definitions

Ingestion means admitting external records into a defined internal representation. A parser can read a
string successfully even when its interpretation is unsuitable. A source saying London 01:30 during the
spring gap is like naming a nonexistent address: adding an offset does not make that address valid.

**Wall time:** calendar fields shown on a local clock. **Offset:** local time minus UTC. **Named zone:**
a location's historical clock rules. **Fold:** a repeated local interval. **Gap:** an interval skipped by
a forward clock change. **Round trip:** convert to UTC and back to check the original interpretation.
**Version key:** asset, feature, observation instant and publication instant, used to detect duplicates.

The policy requires explicit offsets for all timestamps. For an ambiguous label, either valid offset
is acceptable; the source must supply it. Missing offsets are rejected even on ordinary dates. The code
checks internal consistency, not whether the source really published a value at its claimed time.

## Mathematics and worked example

Write a source timestamp as wall fields w and explicit offset u. Its proposed UTC instant is t = w - u.
Let R_z(t) convert t into the declared zone z. Admission requires wall(R_z(t)) = w and offset(R_z(t)) = u.
Checking only t is insufficient: any fixed offset may define an instant even for a missing local label.

For an observation, let o be its observation instant and a its availability instant. Require a >= o.
A version key is K = (asset, feature, o, a). Two rows with equal K are rejected, even if their values agree.
A revision keeps o and changes a. At decision d, the existing selector considers only a <= d, with any
configured processing latency and maximum age still applied in elapsed UTC time.

| Synthetic London input | UTC interpretation | Admission |
|---|---|---|
| 25 Oct 01:30, +01:00 | 25 Oct 00:30 | Accept first occurrence |
| 25 Oct 01:30, +00:00 | 25 Oct 01:30 | Accept second occurrence |
| 29 Mar 01:30, +00:00 | 29 Mar 01:30, returns as 02:30 | Reject gap |
| 29 Mar 01:30, +01:00 | 29 Mar 00:30, returns as 00:30 | Reject gap |

The first version is observed and published at the first autumn 01:30, with value 1. A revision arrives
at the second 01:30 with value 2. Decisions at 00:30 UTC and 01:30 UTC must therefore return 1 and 2.
The two identical wall labels are one hour apart. A duplicate written with Z instead of +00:00 remains
the same version; spelling changes do not create new information.

Not every clock change is an hour. The Lord Howe fold fixture maps 01:45 at +11:00 to 14:45 UTC on
the previous date, and 01:45 at +10:30 to 15:15 UTC. Our validation makes no one-hour assumption.

## Implementation and reproduction

The reusable adapter is src/quant_research/data/ingestion.py. It accepts mappings with exactly five
fields: asset, feature, observed_at, available_at and value. Identifiers must be printable nonempty
strings without edge whitespace. Values are finite built-in integers/floats, excluding booleans.
Each timestamp has seconds, at most six fractional digits and Z or an explicit +/-HH:MM offset.
Unknown -00:00 offsets, naive labels, leap seconds and extra precision fail; none are silently repaired.

A single IANA source_zone applies to both fields of every row. London summer timestamps expressed in
UTC should enter a UTC-declared batch; a London-declared batch requires its local labels and correct
offsets. Seasonal offset changes within one named zone are valid. This is a declared representation
contract, not a prohibition on converting between zones before ingestion with preserved provenance.

The adapter converts and validates every record before returning an immutable tuple in input order.
Errors identify the row and rule without echoing source values. It does not mutate mappings. A failing
iterator is consumed up to its failure; there is no promise of rolling back external side effects.

Run make ingestion-experiment for the diagnostic and make check for the complete checks. The experiment
accepts --output PATH for scratch replays. Run make manifest-experiment for prior provenance evidence;
run make note NOTE_DATE=2026-09-27 to rebuild this note. Runtime dependencies are unchanged.

## Limitations and interview explanation

Structural validity does not prove data entitlement, a truthful publication clock, vintage completeness,
correct security identifiers or trading-session membership. Direct Observation construction still assumes
upstream validation; this is an explicit adapter, not a repository-wide file ingestion service. Raw-file
parsing, persistent cross-batch uniqueness and calendar validation remain separate responsibilities.

Duplicate detection covers one batch. The selector retains its duplicate check when batches are combined.
Raw source text, zone metadata and timezone-database provenance must be retained upstream because the
returned observations store UTC only. Available system/IANA rules are not a pinned embedded database;
expected-offset fixtures expose relevant changes but do not certify all historical dates.

Floating-point conversion can round large integers or decimals; this interface is for scalar research
features, not exact monetary accounting. There is no data download, subscription, new runtime dependency,
measured trading result or performance claim. Q004a still blocks empirical research until access is verified.

For an interview, explain the difference between parsing, validating and authenticating a timestamp.
Draw both autumn instants and a missing spring label. Show the UTC round-trip equations, explain why an
explicit offset resolves a fold but cannot rescue a gap, and finish with the duplicate-version invariant.

## Suggested answers

1. A fixed offset identifies a proposed instant, but its local fields and offset may disagree with
London's rules. Convert through UTC back into London and compare both fields and offset.

2. The fold genuinely contains two instants with the same wall label, each with a valid offset. A gap
contains no instant with that label. Neither proposed gap interpretation returns to the original label.

3. They denote the same zero offset and are duplicates when the remaining version-key fields match.
A later availability instant for the same observation creates a distinct revision.

4. No. The function returns only after validating the whole batch. A source iterator has still been
consumed through the failing row, so callers needing replay must retain or reconstruct their input.

5. No. It checks internal structure and clock consistency. Access rights, truthful availability,
historical vintages and calendar membership need independent evidence and additional validation.
